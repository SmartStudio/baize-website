企业引入自动化工具后，Agent 效果评估要先看团队的活有没有做完，再看模型被调用了多少次。接口调用次数、开通账号数或请求量，只能说明工具被点开了，说明不了工作有没有变得更省事。做好 Agent 效果评估，核心要盯住四类指标：业务从发起到完成的总耗时与交付量、人工介入修改与返工的比例、员工在不同助手之间切换与核对输出的摩擦成本，以及多个助手功能重叠的情况。每个指标都要建立上线前的基线，按具体业务团队分别统计，不搞全公司笼统平均。

## 调用量繁荣背后的评估误区

很多企业的看板上，放在最前面的是调用次数、Token 消耗量和活跃用户数。

用量大不等于价值大。员工对同一个助手反复问，常常是因为答非所问，只好改提示词重来。看板上显示活跃度高，业务上其实是返工。按量计费模式下的成本管控逻辑，可对照 <NoteLink slug="ai-usage-pricing-budget">AI 按量计费后，企业一年一编的预算还管得住吗？</NoteLink>。

把调用量当成效果，团队容易去想办法让员工多点几下，流程卡在哪里还是看不出来。评估要看业务交付的结果。

## 事实数据：管理层与一线员工的感知鸿沟

CIO Dive 2026 年 10 月 16 日报道了 Asana 针对美国和英国 4,500 多名 CIO、AI 负责人与员工的调查报告。数据显示，68% 的领导者每周使用三个或更多 Agent，而在普通员工中这一比例只有 36%。更关键的是，不到四分之一的员工认为现有的 Agent 能够处理他们最需要帮忙的任务。

调查还揭示了工具泛滥带来的隐性损耗：在日常使用 Agent 的员工里，近一半表示大约 10% 的工作时间花在了切换工具、确认该用哪个 Agent、管理输出以及处理冲突上；38% 的受访者反映，超过四分之一的 Agent 工作存在重复或重叠。

对此，Asana 首席产品官 Arnab Bose 指出，CIO 应当少看 Agent 的活动量，开始衡量工作是否真正完成、哪些工作对团队和业务最重要。报告还提到，天天和 Agent 一起干活的员工，更容易发现 Agent 在上下文不全时行动、给出互相冲突的输出，他们的谨慎是有依据的。我们的看法是，管理层别把这种谨慎当成消极抵触。培训与真实流程脱节的问题，可参考 <NoteLink slug="all-hands-ai-training-workflow-unchanged">企业 AI 培训完了 vs 工作流没改</NoteLink>。

## 效果评估该抓的四类核心数据

第一，业务交付周期与完成总量。从项目管理系统或工单后台中提取数据，统计特定业务（如客诉响应、报表出具、合同初审）从任务创建到最终交付的时长。对比引入自动化前后，同等周期内团队完成的工单总量是否提升、单件流转时间是否缩短。

第二，人工返工与修正比例。统计业务产出物在交付前被人工修改的幅度。如果一篇研报初稿由 Agent 生成后，分析师需要删改大半内容；或者生成的代码提交后在审查环节被打回重写，往往意味着工具产出无法直接交付。通过比对初稿与终稿的改动比例，可以准确衡量助手的可用度。

第三，工具切换与核对损耗。评估员工为了配合 AI 工具额外付出的沟通与校验成本。如果一个任务需要员工在三四个不同助手之间来回倒腾数据，或者需要耗费大量时间逐字排查模型的输出是否包含编造数据，这些摩擦损耗抵消了自动化带来的收益。

第四，功能重复与输出冲突率。观察团队内部是否存在多个助手做同一类事情的情况。多个部门各自拉起功能相近的工具，容易造成数据源不统一、口径打架，带来额外的对账成本。

## 建立业务基线：按团队算，不按全公司平均

不同岗位的业务逻辑差别很大：法务审查合同注重条款严谨，研发写代码注重单元测试通过率，销售整理线索注重时效性。把所有部门的调用混合在一起算一个全公司平均提效，看不出哪里该改。

更好的做法是按业务团队划分评估单元。在某个助手上线前，先记录该团队处理同类任务的历史基线数据：过去人工处理平均耗时多久、错误率是多少、每个月能承接多少业务量。上线经过一段时间的磨合后，再用相同口径统计当前数据，通过前后对比客观判断工具的作用。

## 数据呈现后的三项优化动作

首先是清理与合并。对于功能重叠的助手进行合并，停掉长期无人问津的闲置配置，把零散的工具收拢为规范的公共流程。

其次是调整开发优先级。对照一线员工的真实痛点，把开发资源先投到员工说最需要帮忙、但现有 Agent 还处理不好的任务上。

最后是补齐上下文供给。很多时候助手答不好，根源在于权限和数据源没接通。针对返工率偏高的环节，针对性地提供结构化数据库或业务知识库，减少因为信息缺失造成的试错。

数据源接通后，指标口径不统一还会让 AI 问数给出两个答案，处理办法见 <NoteLink slug="ai-data-query-metric-definitions">AI 问数问出两个销售额，指标口径该信哪个？</NoteLink>。

## Agent 效果评估：常见问题

### 调用次数和 Token 消耗量，在效果评估中完全没用了吗？

调用次数和 Token 消耗属于成本指标与健康度指标，不属于价值产出指标。它们主要用来核算算力开支、监控系统负载是否平稳、排查是否有脚本死循环调用。看工具究竟给公司省了多少时间、办了多少事，要看业务交付结果，不能把成本消耗当成产出业绩。

### 一线员工对新工具表现出谨慎甚至观望，管理层该如何看待？

一线员工谨慎，多半是因为他们天天看到 Agent 出错的地方。正如调查报告指出的，直接操作业务的员工最清楚模型在缺乏上下文时的局限性。硬推全员使用，反而可能导致错误数据流向下游。管理层应当重视员工反馈的具体卡点，把员工指出的高频报错和返工场景，作为优化提示词与补充系统数据的关键输入。

### 团队如何采集数据，来客观统计端到端的业务完成率？

统计端到端业务完成率，要将埋点落在实际流转的业务系统中，不能只停留在聊天框里。技术团队可以在工单、CRM 或代码仓库中设立自动化处理标签：当一项任务由 Agent 发起或流转时，记录其进入自动节点的初始时间；如果该任务未经人工打回、直接通过下游验收并顺利结案，则计为一次成功的自动交付。业务完成率 = 未经打回的结案数 ÷ 进入流程的任务总数。
